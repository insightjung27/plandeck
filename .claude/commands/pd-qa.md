# /pd-qa — QA 수용기준 확인·보강 (테스트 정보 레인)

`$1`=화면ID(또는 전체).

> ★ PlanDeck는 테스트를 '실행'하는 도구가 아니다(테스트 러너는 따로 있다). 여기서 QA는 **자기 테스트 설계에
> 필요한 정보** — 화면별 상태·예외·수용기준 — 을 한곳에서 **확인**하고, 기획자가 놓친 케이스를 함께 메운다.
> PlanDeck의 cases는 그대로 **수용기준(Given-When-Then)**이자 **테스트 케이스 명세**이므로, QA는 "코드보다 먼저"
> (shift-left) 무엇을 테스트할지 합의한다. 결과는 `/pd-handoff`의 QA 테스트플랜(.feature)으로 방출되어
> QA가 자기 러너·수동 테스트에 그대로 투입한다(실행은 거기서).

> 리추얼(벤치마크: Three Amigos): 기획·개발·QA가 cases 매트릭스를 함께 보며 "무엇을 어떻게 테스트할지"를
> 구현 전에 합의한다. QA는 기획자가 놓친 예외·엣지·적대 입력을 메운다.

## 절차

### 1) 대상 로드
- `config/screens.js`에서 `$1`(또는 전체) + 각 화면의 `cases`·`interface`·`components`·`flow.to`를 읽는다.

### 2) QA 완결성 검증 (적대적)
각 화면에 대해 점검:
- **상태 커버리지**: 화면상태 7종(초기/로딩/정상/빈데이터/에러/권한없음/엣지)이 모두 정의 또는 N/A인가? 빠진 상태를 지적.
- **입력검증 5종**(입력 폼이 있으면): 필수누락·형식오류·범위경계(min-1/max+1)·중복충돌·유효가 필드별로 있는가?
- **엣지/적대 입력**: 긴/빈 문자열, 특수문자, 비US 우편번호, 동시요청, 네트워크 단절, 중복제출, 뒤로가기/타임아웃 등 누락 보강.
- **API 결속**: 에러 cases(403/404/409/5xx)가 interface writes의 errors[]와 일치하는가? 불일치 지적.
- **메시지 품질**: 안내문구가 저작된 사용자 카피인가(백엔드 raw 금지)? 복구액션·표시위치(placement)가 있는가?

### 3) cases 보강 + QA 메타 부여
- 누락 케이스를 `cases[]`에 추가(형식은 /pd-cases와 동일).
- 각 case에 QA 메타(선택) 부여:
  ```js
  { state:'형식오류', trigger:'제출', guard:'이메일 형식 오류', result:'제출 막음',
    message:'이메일 형식이 올바르지 않습니다', placement:'inline', target:'.pd-input-email',
    priority:'P1', testId:'TC-LOGIN-003' }      // ← QA 메타
  ```
  - `priority`: P0(치명)/P1(주요)/P2(사소)
  - `testId`: 테스트 케이스 ID(추적성)

### 4) 리포트
- 화면별 QA 체크리스트(통과/보강/실패)와 보강한 케이스 요약. 미해결 리스크는 openQuestions나 별도로 남긴다.
- 다음: `/pd-handoff`로 QA 테스트플랜(.feature + 체크리스트)을 방출해 QA 러너/수동 테스트에 투입.

## 주의
- QA는 cases를 **보강**한다(기획자 콘텐츠를 지우지 않는다). state는 고정 enum 유지.
- 테스트 '결과' 추적은 QA 러너/별도 시트에서(이 툴은 '테스트 설계·수용기준'의 SSOT). 엔진 파일 수정 금지.
