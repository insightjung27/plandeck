# 팀 운영 — 역할별 활용 가이드

PlanDeck의 핵심 원칙: **각 역할은 자기 업무를 각자의 전문 도구에서 수행하되, 그 업무에 필요한 "정보"는
모두 PlanDeck 한곳에서 확인한다.** PlanDeck는 디자인 툴·IDE·테스트 러너를 대체하지 않는 **명세 단일 참조소(SSOT)**다.

```
          ┌───────────────── PlanDeck (기획 명세 SSOT) ─────────────────┐
          │  PRD · 화면 · 기능/버튼 · 경우의수(예외) · 개발 인터페이스 · 흐름   │
          └───────────────────────────┬────────────────────────────────┘
      확인/저작      확인(연결)        확인(수령)        확인(수령)       확인(열람)
    ┌──────────┐  ┌──────────┐    ┌──────────┐     ┌──────────┐    ┌──────────┐
    │  기획자   │  │ 디자이너  │    │  개발자   │     │   QA     │    │ 의사결정자 │
    │ (저작)    │  │ →Figma   │    │ →IDE     │     │ →테스트러너│   │ 검토모드  │
    └──────────┘  └──────────┘    └──────────┘     └──────────┘    └──────────┘
```

---

## 역할별 상세

### 1) 기획자 — 유일한 **저작** 역할 (상위 PRD → 디테일 기획)
- **상위 기획**: `/pd-prd` 로 PRD(배경·목표·사용자·범위·지표·제약·릴리스 + 워크플로)를 작성.
- **기본 틀 자동 생성**: `/pd-scaffold` 로 PRD에서 화면 인벤토리+플로우를 '맵 선행'으로 펼치고, **승인 후** 빈 화면 생성.
- **디테일 기획**: 화면별로 `/pd-wireframe`(기능·버튼) → `/pd-cases`(예외) → `/pd-interface`.
  - ★ `/pd-interface`는 **개발자 협업 단계**다: 기획자는 '무엇을·왜'(의도·데이터 객체·사용자 에러 문구)를 적고,
    method/path/status/멱등/인증 같은 **기술 계약은 개발자가 확정·보완**한다. 비개발 기획자가 혼자 추측하지 않는다.
- 산출: `index.html`(개요) · `prd.html`(PRD) · `spec.html`(상세 기획서) — 팀·의사결정자가 읽는 **상세 작업용 기획 문서**.

### 2) 디자이너 — **확인 후 Figma에서 작업, 결과를 연결**
- **여기서 확인**: 어떤 화면을, 어떤 구성요소(components/버튼)로, **어떤 상태(cases: 로딩/빈데이터/에러/권한없음…)까지**
  디자인해야 하는지. 상태 커버리지가 곧 "디자인해야 할 화면 변형 목록"이다.
- **실제 디자인은 Figma에서.** 완성 후 `/pd-figma-sync <화면ID> <figma url>` 로 시안을 **연결**(designed:true).
- 디자이너는 PlanDeck에서 픽셀을 그리지 않는다 — "무엇을 그려야 하는지"를 빠짐없이 확인할 뿐.

### 3) 개발자 — **확인 후 IDE에서 구현**
- **여기서 확인**: INTERFACE 패널(🔌)에서 화면별 API/데이터 계약(reads/writes/events·엔티티·에러·인증·멱등),
  CASES 패널(🧩)에서 분기/예외, 플로우에서 '어느 버튼→어느 API→다음 화면'.
- **받아가기**: `/pd-handoff`(또는 handoff.html)에서 **OpenAPI 3.1 JSON**(mock·SDK 생성), **마크다운 스펙**,
  **에이전트 번들 JSON**(코딩 에이전트 입력)을 내려받는다.
- **추적성**: 화면 ID(예: `SCR-PAY-001`)를 브랜치·커밋·PR에 넣어 기획↔구현을 연결(예: `feat/SCR-PAY-001`).
- 실제 코드는 IDE에서. PlanDeck는 "무엇을 어떤 계약으로 구현해야 하는지"의 정본.

### 4) QA — **확인 후 러너에서 테스트**
- **여기서 확인**: 화면별 **수용기준(Given-When-Then)**, 상태 커버리지(빠진 상태=빨강셀), 입력검증(EP/BVA).
- **보강**: `/pd-qa` 로 기획자가 놓친 엣지·적대 입력·조합 케이스를 함께 메우고 우선순위(P0~P2)·testId 부여.
- **받아가기**: `/pd-handoff` 의 **QA 테스트플랜(.feature + 체크리스트)** 을 내려받아 자동화/수동 테스트에 투입.
- 테스트 '실행'은 러너에서. PlanDeck는 "무엇을 어떤 기준으로 통과로 볼지"의 정본(shift-left).

### 5) 의사결정자 — **검토 모드로 프로토타입 확인·결재**
- 배포 링크(GitHub Pages)를 받아 브라우저로 연다 — 설치·계정 불필요.
- **검토 모드**(우측 상단 👁 또는 `?mode=review`): 기술 패널(계약·예외) 숨기고 **화면+플로우 프로토타입만** 깔끔히.
- 플로우 노드/목록을 클릭하며 사용자 여정을 따라 둘러보고, `spec.html`로 상세 근거를 확인해 의사결정.

## 역할 레인 & 충돌 방지

CODEOWNERS는 **파일/디렉터리 단위로만** 리뷰어를 지정한다(한 파일의 JSON 하위 키를 역할별로 쪼갤 수 없다).
따라서 잠금은 경로 단위로, 역할 책임은 **합의된 작업 범위 + 작은 PR**로 지킨다.

| 경로 | CODEOWNERS 소유 (`.github/CODEOWNERS`) | 비고 |
|---|---|---|
| `engine/**` · `.claude/commands/**` · `templates/**` | 운영자(키트 주인) | 팀원 열람만 — 변경 시 운영자 리뷰 강제 |
| `projects/<slug>/**` | (선택) 프로젝트 담당 | 프로젝트 단위 소유 지정 가능 |

`projects/<slug>/config/screens.js`는 **여러 역할이 함께 편집하는 공동 파일**이다(한 화면 객체 안에 기능·예외·계약이 동거). 역할 책임은 소유가 아니라 작업 범위로 나눈다:
- **기획자** = PRD·화면·기능·예외(의도·흐름·사용자 문구)
- **디자이너** = `figmaLink`·`designed`
- **개발자** = `interface`의 method/path/status/멱등 등 **기술 계약**
- **QA** = `cases` 보강·`priority`·`testId`

> **충돌 완화 = 작은 PR이 기본.** 화면이 수십 개로 늘어 충돌이 잦아지면 **화면별 파일 분할**(opt-in 고급 패턴, OPERATIONS §3)로 전환한다. (분할은 기본값이 아니라 선택 — 과용 금지.)

## 협업 리듬 (권장)

1. **킥오프**: 기획자가 `/pd-prd` → `/pd-scaffold`로 맵 초안. 팀이 맵(화면 인벤토리·플로우)을 함께 리뷰·승인.
2. **디테일 스프린트**: 기획자가 화면별 wireframe→cases→interface. 완료분은 PR.
3. **Three Amigos**: 기획+개발+QA가 cases 매트릭스를 함께 보며 수용기준 합의(구현 전). 디자이너는 상태 변형 확인.
4. **핸드오프**: `/pd-lint`로 완결성 확인 → `ready-for-dev` 동결 → `/pd-handoff`로 개발·QA에 전달.
5. **결재**: 의사결정자가 검토 모드로 프로토타입 확인 → 승인/피드백. (PlanDeck는 열람·확인 도구이므로
   승인/코멘트는 **git PR 리뷰 코멘트** 또는 별도 채널로 남긴다 — 도구 내 전자결재 기능은 없음. 결정 흔적은 PR에.)
6. **변경 관리**: 승인 후 스펙이 바뀌면 "변경됨" 배지 → 재검토 루프.

> 동기화는 전부 **git(PR)** 으로. 외부 라이브 싱크·백엔드 없음(무빌드·정적 유지).
